# 仕組み

日本語 | [English](how-it-works.en.md)

[README](../README.md) に書ききれない、データの取り方と地球儀ビューアの作りをまとめます。

## データの取り方

1. **リソースマニフェスト**（protobuf）を取り、Flyover のタイル（style 15）の URL と、認証に使う `tokenP2` を得る
2. マニフェストに書かれた**高さ区分の一覧**（`altitude-*.xml`）から、地点を含む地域を選ぶ。地域の名前 `Reg_z9_X_Y` は、その地域が覆うズーム 9 のタイル番号
3. タイルを `x, y, z, h` で要求する。URL には `sid` と `accessKey`（AES-256-CBC で作る）を付ける
4. **C3M**（1 タイル分の 3D モデル）を読む。メッシュは Apple 独自の Edgebreaker の変種で圧縮されている（ハフマン符号 → CLERS 文字列 → 角の表 → 平行四辺形予測で頂点と UV を復元）。画像は HEIC
5. 地心座標（ECEF）を東・北・上（メートル）に直し、HEIC を JPEG にして、ブラウザ用に書き出す

衛星画像は style 7、地形は style 17（ズーム 7 と 11 は全世界、13 は米国と欧州）。版はマニフェストの style の設定にある。

## 地球儀ビューア

### タイルの選び方

- Flyover のタイルはズーム 13（1 枚約 4 km）〜20（約 30 m）まである。ビューア（CesiumJS）は、ズーム 9 の地域から四分木をたどり、画面で大きく見える（画面の画素で 520 px を超える）タイルほど細かいものを選ぶ
- 途中の階層は 1 段おきにしか読まない（読む量が 4 割ほど減る）
- 子孫で埋め尽くせる 4 分の 1 から細かくする。まだ埋まらない所や、子にデータがない所（水面など）は、親をその 4 分の 1 だけ切り出して描く
- 必要なタイルが届くまでは、手元にある細かいタイル（3 段下まで）か粗いタイルで埋め、動かしている間に 3D が消えないようにする

### 読み込みの順番

- 同時に読むのは 48 枚まで。それ以上並べても回線が埋まっていて速くならない（手元の 50〜65 Mbps の回線で、48 本で上限に達し、96 本では 1 枚ごとの待ちが延びるだけだった）
- 画面に見えているものを先に、大きく見えるものから読む。カメラのまわり（高度の 2.5 倍、粗いタイルはその 4 倍まで）の画面の外のものは、見えているものが全部届いてから先読みし、回したときにすぐ出せるようにする

### ブラウザの負担を減らす工夫

- 止まっているときは描かない（Cesium の requestRenderMode）。カメラが動いたときと、読み込みや動きのあるときだけ描く
- 読み込み中に時間を取るのは、シェーダーの用意（GPU 向けの翻訳）と、画像を GPU に送ること。Flyover のモデルは光を当てない（写真そのまま）ので、Cesium の映り込み（動的な環境マップと IBL）と `Scene#pick` 用の準備を切っている。映り込みは準備ができたところでシェーダーを全部作り直させ、読み込みの最初の数秒をそれに取られていた（シェーダー 74 本 → 53 本）
- 下の帯のカーソルの標高と縮尺は、カメラもマウスも動いていなければ 1 秒ごとにしか調べない（深度を読むと GPU を待たせる）
- 地球儀が 1 コマで読み込みを進める時間を、5 ms から 20 ms にしている

### サーバーでの変換

- 高さ区分をまとめて 1 つの glb（頂点は地心座標）にし、`cache/glb4/` に置く
- 頂点の位置は int16、UV は uint16 に詰める（KHR_mesh_quantization。4.9 km のタイルでも 8 cm 刻み）
- 新しい Flyover の画像は、ブラウザが HEVC を GPU の専用回路で展開できるとき（WebCodecs。Chrome はソフトウェアでは展開しない）は、JPEG にせず HEVC のまま渡す（`?hevc=1`、`cache/glb98_15h/`）。HEIC の中身は HEVC の 1 コマだけなので、設定（hvcC）とコマを材質の `extras.hevc` に入れる。ビューアは作業用のスレッド（`earth/hevc.js`）で展開し、明るさ（Y）と色（UV）の面をそのまま Cesium の CustomShader のテクスチャにして、シェーダーで RGB に直す。HEIC には色の決め方が入っていないので、HEIF の決まりどおり BT.601 のフルレンジとして扱う（pillow_heif と同じ。Chrome は何も言わないと BT.709 のリミテッドレンジとみなす）
  - サーバーで glb を作る時間は、高さ区分 1 つで 125 ms から 19 ms ほどになる（HEIC の展開・縮小・JPEG がなくなる）。ブラウザでの展開は 1 枚 10 ms ほど
  - 画像は元の大きさのまま（配列から作るテクスチャは、WebGL2 では 2 のべき乗に広げられない）で、1 画素 1.5 バイト。大阪で 208 タイルを読み込んだとき、GPU の画像は 438 MB（2 のべき乗に縮めた JPEG なら 754 MB、縮める前は 2,885 MB）
  - どの材質の画像かは、頂点の属性 `_SLAB`（位置の 4 つ目の int16。もとは詰め物）で分ける。展開できなかったら、以後は JPEG で受け取る。`?hevc=0` を付けると JPEG だけにする
- 画像は縦横をそれぞれ 1 つ下の 2 のべき乗に縮める。Cesium は 2 のべき乗でない画像を、縮小用の段（ミップマップ）を作る前に次の 2 のべき乗まで広げるので、新しい Flyover に多い 1152〜1376 px の画像が 2048 px になり、GPU のメモリが 2.5 倍ほどになっていた（大阪で 314 タイルを読み込んだとき、画像が 3.6 GB から 1.0 GB ほどになる見積もり）
- Flyover の範囲の端のタイルには、平らな地図につなぐための灰色の帯（メッシュの種類 4）と高さ 0 の面（種類 3）が入っている。地形の上では 2 層に見えるので入れない
- 高さ区分はタイルの大きさに比べた高さの区切りで、ズーム 16 以下では h = 0 しかない（東京スカイツリーやデンバーでも）。そのため、ズーム 15 以下は h = 0 だけ、16 は h = 0〜1 だけを要求する
- C3M の展開は、numba があれば重い部分（`flyover/_fast.py`）をコンパイルして速くする（密な街で 1 枚 0.3 秒 → 0.06 秒。結果は純 Python 版とビット単位で同じ）。起動時に立ち上げておいた別プロセスで並べるが、ブラウザと CPU を取り合わないよう、コアの 4 分の 1（多くて 4 つ。1 つ 140〜190 MB のメモリを使う）で、優先度を少し下げて動かす

### Apple への要求

- HTTP/2（httpx）で、4 本の接続の上にそれぞれ同時 90 本まで並べる。Apple は 1 枚に 1 秒ほどかかるが、並べるほど速い（requests の HTTP/1.1 では、接続ごとの TLS の確立などで、同時 32 本で応答まで 4 秒ほど待たされた）
- 1.5 秒たっても返らなければ、同じ要求を別の接続でもう 1 本出し、先に返ったほうを使う（まだなら 3 秒後に 3 本目）
- 1 本は 10 秒であきらめる。接続ごと止まっている（しばらく何も返っていない）ときは張り直す（以前は 60 秒待たされることがあった）
- 地形と衛星画像は Flyover のタイルと別の接続で取る。ただし Flyover のタイルを 16 本以上取っている間は、同時 4 本までに絞る。回線はどちらでも埋まり、地面の画像の多くは 3D の街の下に隠れるので、街を先にしたほうが早くきれいになる

### 地形

- 地形は 16 bit の PNG。PNG の終わり（IEND）の後ろに付いた 12 バイトに、float32 の基準の高さと倍率（0.25）が入っている（高さ = 基準 + 値 × 倍率）
- 高さは Flyover と同じ楕円体高で、基準はタイルごとに違う（読み落とすと、内陸では何百 m も低くなる）
- Cesium の地理座標のタイルに直して渡す
- EGM96 のジオイド高（初回に PROJ の配布物から 2.7 MB 取る）は、地形のタイルのない所の海面と、画面に出す標高に使う

### そのほか

- ブラウザの同時接続の上限（同じホストに 6 本）を避けるため、Flyover・衛星画像・地形のタイルは、ループバックの別のアドレス（127.0.0.2〜127.0.0.17）に振り分けて取る
- 地名の検索は OpenStreetMap の Nominatim に中継する

## 2026 年のサーバーで変わっていたこと

移植元の retroplasma/flyover-reverse-engineering（2021 年にアーカイブ）から、次の点が変わっていた。ここではそれに合わせてある。

- マニフェストのファイル置き場（`cache_base_url`）が空になった → `https://gspe21-ssl.ls.apple.com/` を使う
- 地域ごとの目録 C3MM 第 1 版（style 14）が 404 になった（タイル座標で取る第 2 版 style 52 は返るが、形式が未解読）→ 目録を使わず、範囲のタイルと高さ区分を直接要求して、空の応答を飛ばす
- C3M の 5 バイト目（版）が 3 から 7 になった → 第 3 版の読み方でそのまま読める
- 画像が JPEG から HEIC（画像の形式 13）になった

また、元のツールは地域を「中心がいちばん近いもの」で選んでいて、地域の重なる東京などでは外れる（渋谷は 1 枚も取れなかった）。ここでは地域の名前 `Reg_z9_X_Y` のタイル番号で選ぶ。

認証の手順と `tokenP1` は [sk-zk/streetlevel](https://github.com/sk-zk/streetlevel) の Look Around 用の実装と同じ（あちらも retroplasma から来ている）。retroplasma の設定手順は、`tokenP1` を取り出すために Xcode のシミュレータ SDK（約 2 GB）をダウンロードするが、ここでは不要。

## 新しい Flyover（style 98）

iOS 27 として要求したマニフェストには、新しい Flyover のタイル（style 98）が載っている。`python scripts/earth.py --r3d` で起動すると、すべてのズームでこちらを使い、新しい Flyover のないタイルと読めないタイルだけ今までの C3M で補う（ズームで新旧のデータが切り替わって景色が変わらないように）。読み取りは `flyover/r3d.py`。

- **取り方**: タイルの番号の付け方と高さ区分は C3M と同じ。`?style=98&v=<style 98 の版>&region=<地域>&x&y&z&h` で要求する（`v` は地域の版ではなく style 98 の版）
- **ファイル**: 先頭が `3D 96 59 2E` の入れ物に、三角形のスプラット（part 1）と、テクスチャ付きのメッシュ（part 2）が入っている。メッシュの座標は、part 2 の最初の項目にある 3×3 の回転と平行移動で地心座標（ECEF）になる。テクスチャは part 2 の画像の項目（項目 3）で、テクスチャが何枚かあれば項目 3 がその数だけ並ぶ（手元の 36,695 枚のうち 3,317 枚。福岡のように古い Flyover の形をそのまま入れた所に多い）。それぞれの最初の HEIC がテクスチャ
- **スプラット**: 木などは、メッシュではなく三角形のスプラットで表されている（公園のタイルではメッシュが小さく、スプラットが 2 万枚近くある）。1 枚ごとに頂点 3 つ、色と不透明度、4 つの値を持つ（下の「スプラットの 4 つの値」）。Apple は三角形の内側ほど濃く、縁で消えるように描いている。glb では、頂点の色（RGBA）を付けた半透明の三角形にし、縁ほど透明になる共通の小さな画像を貼って近い見た目にする（Apple の描き方とは画素単位では一致しない）。半透明なので、低いものから順に並べて描く（奥から描かないと手前の色が奥の色に塗られて濁る。視点はたいてい上なので、高さの順で足りる）
- **スプラットの見え方の合わせ込み**: iOS 27 のマップで撮った夢洲（大屋根リングの中の森）の画面 3 枚と比べた。画面と書き出しの特徴点を対応させて、Apple のカメラの位置と向きを求め（PnP。縦の画角はどの画面も 30°、ずれの中央値 0.5 画素）、同じ視点で描いて木のところの明るさの相関を見た。並べずに描くと 0.83〜0.87、低いものから順に描くと 0.91〜0.95（視点ごとに奥から並べ直しても同じ）。縁のぼかしの指数は 0.25〜3 のうち 1.5 がいちばん近く（0.95〜0.97）、スプラットの 1 番目の値を 1 枚ずつの指数にすると、どの倍率でも一律の 1.5 より少し遠い
- **圧縮**: 中身は C3M と同じ Edgebreaker の変種を、流れごとに分けて詰めたもの。数の列は「レーン」ごとに、ビットマップ（1 で次の値、0 で直前の値をくり返すか表を引く）と、ハフマン符号（Apple 独自の表の書き方）で詰めてある
  - **形**: 三角形ごとの C / それ以外のビットと、それ以外の 2 ビットの種類を、旧 C3M の 1 本のビット列に組み直し、`edgebreaker.py` で三角形にする
  - **位置**: 頂点ごとの整数 × 刻み。三角形を幅優先でたどる平行四辺形の予測との差が入っている
  - **UV**: 三角形ごとの 4 ビットが UV の継ぎ目の印。UV の番号は継ぎ目を境に深さ優先で振り、値は継ぎ目を境にした幅優先の平行四辺形の予測で戻す。単位は 4 分の 1 テクセル
  - **レーンの目録（J）**: 使うレーンのビット、レーンごとの 2 ビットの種類（m 本なら 2m + 6 ビットの欄）、レーンごとの長さと埋め方の印。種類は「次のレーンで何が変わるか」を表す。上のビットが 1 なら次のレーンの長さを書き（0 なら同じ長さ）、下のビットが 1 なら次のレーンの埋め方の印を 1 バイト書く（0 なら同じ埋め方）。1 本目の印は種類のビットのあとのバイトの区切りに入る（m が 4 で割って 1 余るときは欄に入らず、印はない）。印は 0 = 生のバイト列、1 と 4 = くり返し、2 と 5 = 表引き、3 と 6 = 符号つき差分（1〜3 と 4〜6 の違いは分からない）
  - **スプラット**: 位置（XYZ）と属性 8 つの BYET ブロック。原点は、成分ごとの 4 バイトか、それを短く詰めたもの。詰めたものの一つは、それ自体が小さな BYET（int のバイトをレーンに、成分を値として並べたもの）になっている
  - **法線**: 2° 刻みの球面座標で入っている（光を当てない表示なので、今は読まない）
- **速さ**:
  - 重いループ（ハフマン符号、レーンの埋め方、3 つのたどり、予測の再生）は numba で動かす。1 枚 20〜150 ms で、Python のままの 5〜13 倍の速さになる。
  - ハフマン符号の表の読み取りと、三角形のつながり（CLERS）の展開も numba で動かす。新しい Flyover の高さ区分 1 つを読む時間は 36 ms から 23 ms ほどになった（手元の 4,838 タイルで、結果は前とまったく同じ）。
  - 壊れたデータでもプロセスが落ちたり止まったりしないよう、numba に渡す前に添字の範囲を確かめ、角の表をたどるところは添字を確かめる設定（`boundscheck`）で動かし、回る数に上限を付けている。
  - タイル 1 枚の作成では、画像（HEIC）の展開（100〜150 ms）がいちばん重い。
  - 新しい Flyover はまだ Apple の配信サーバーに溜まっていないことが多く、初めて取るタイルは応答に 1〜2 秒かかる（2 回目からは数十 ms。手元でも `cache/r3d/` に残す）。
  - z16 以下の新しい Flyover は 1 枚 1 MB 前後と大きいので、初めての場所では遠景が出るまでに 1〜2 秒かかる。取得が時間切れになったタイルは C3M で埋めず、ビューアがあとで取り直す。
- **検証**: Apple 自身の展開結果（iOS 27 のシミュレータで書き出されたもの）が公開されている東京の 29 タイルで、メッシュの三角形・位置・UV の番号・UV の値と、スプラットの頂点・色・属性がすべてビット単位で一致する
- **読み方の出どころ**: Apple の説明はない。[nmt3325/apple-maps-r3d-research](https://github.com/nmt3325/apple-maps-r3d-research) の文章（コードは読んでいない。ライセンスがないため）を手がかりに、データから割り出した。照合に使った正解データも同じリポジトリのもの
- **レーンの埋め方**: J の印で決まる（手元のタイルのスプラットの約 15 万レーンで、印と、データから割り出した埋め方が全部一致する）。印のないレーンでは、予測が当たるところはビット 0 になるので、正しい埋め方ではリテラルが予測と同じになることはない、という性質で選ぶ
- **メッシュの欄の区画**: 三角形の数、あらかじめ貼り合わせる角の組 (va, vb)、頂点の数などの int32。欄を 4 バイトずつ並べたバイト列を、欄ごとの 4 ビットの印（どのバイトを書くか）をビットマップにして、表引き（原点の詰め方のモード 4 と同じ: 書かないバイトは 表[直前のバイト]、書いたバイトを読むたびに 表[直前] = それ）で詰めたもの。先頭が 0C のときは、それをさらにくり返しのビットマップで詰めてある。手元のタイルで、すべての欄がこの読み方で正しく読める
- **見出しの数と小さなタイル**: 見出しの 2 つの数と XYZ のあとの 2 つの数は、小さければ 1 バイト。どれも展開に使う領域の大きさで、数 n を「64 未満ならそのまま、ほかは n + (n ÷ 64 の切り捨て + 1) × 64」にしたもの。見出しの 1 つ目は三角形の数、XYZ のあとの 2 つは UV の数から決まる（手元の 2,487 枚で全部一致。XYZ のあとの 2 つ目は、まれに少し大きい）。見出しの 2 つ目は、C / C 以外の符号列（C は 1 ビット、ほかは 3 ビット）のバイト数のおおよそを同じ式にしたもの（ずれは ±1 バイト。式は詰め切れていない）。読むのには使わない。小さなタイルでは継ぎ目のブロックが、大きな低ズームのタイルでは三角形ごとの C のビットが、詰めずにそのまま、または 1 レーンの BYET で入っている
- **版 1 の入れ物**: 高い区分にまれにある。部分と項目の枠がなく、16 バイト目から回転と平行移動の double が 12 個、続いてスプラット（`D1 22 C9 07` で始まる）、メッシュ（`E1 21 66 24` で始まる）、画像の HEIC が並ぶ。中身は版 2 と同じ形で、同じように読める
- **テクスチャの選び方**: メッシュの区画の「チャートごとの番号」のブロックが、UV のチャート（継ぎ目で区切られたまとまり。たどる順に番号が付く）ごとのテクスチャの番号。int32 の並びで、小さいものはそのまま、ほかは 4 レーンの BYET（値はレーン 0 か、それがなければレーン 1）。テクスチャが 1 枚なら空。UV の値は、そのチャートのテクスチャの画素の 4 倍の単位。福岡のタイルで、同じ所の C3M の材質の分け方と三角形の数まで一致する（以前は最後のテクスチャだけを読んでいたので、こういうタイルは画像がでたらめに貼られていた）
- **くり返して貼るテクスチャ**: 画像の項目 13（値は 1 か 2）があるテクスチャは、水面などの塗りつぶし用の小さな画像（16 px 角のこともある）で、UV は 0〜1 の外に出る。くり返して貼る（glb では標本の取り方を REPEAT にし、HEVC にはしない）。海沿いの低いズーム（z13〜14）のタイルに多い。これを「陸の写真が入っていない」と読み違えていた。XYZ のブロックのあとの余分なブロック（頂点ごとの 1 ビットの印）は、海や湖の縁から外へ 25〜57 m、下へ 66.6 m の斜めの帯の、下側の頂点に付く（印の付いた頂点はどれもメッシュの縁で、水面のテクスチャの三角形だけに属し、高さがそろっている）。帯は水面のテクスチャを貼った斜面で、隣の地面との境の隙間を隠すものらしい。印の使い道（下の縁を消すのか、水の深さに使うのか）は分からない
- **両側の UV が同じ継ぎ目**: 海沿いの z13〜14 のタイルにだけあり（調べた 2,487 枚のうち 4 枚）、どれも陸の写真の三角形の間の辺。1〜2 辺の短い線で、片方の端が海岸線（メッシュの縁）、もう片方が陸の内側で止まる。写真の UV を作るときに面を切り開いた線だが、写真は真上から貼るので、両側の UV が同じになったものらしい。UV の番号はふつうの継ぎ目と同じく分けるが、UV の値の予測ではまたいでたどる
- **読める割合**: 手元に取った 37,542 枚が、すべて読める。最後まで読めなかった海沿いの z13〜14 の 12 枚は、UV の値の予測でたどる順の読み違いだった。海沿いのタイルには、継ぎ目の印が付いているのに両側の UV の番号が同じ辺がある。UV の値の予測は、印ではなく「辺の両側の UV の番号が同じか」で辺を渡る（印で止めると、予測の参照がずれて写真の UV が大きく外れる）。直したあとは、同じ所の C3M と同じ写真の貼り方になる。同じ形の海沿いのタイルで、読めてはいたが写真の UV が少し外に出ていたものも、同じ読み違いだった
- **ずれていた位置と大きなタイル**: 位置の予測で、かたまりの最初の三角形の中点も直前の予測にする（以前はしていなかった）。頂点が 3 つだけのかたまりのあとで位置がずれ、9 枚が読めず、153 枚が一部ずれたまま読めていた。直したあとは、古い Flyover の形をそのまま入れたタイルで、位置も UV も C3M と刻みの範囲で一致する。また、チャートの数（小さな数）は 8,192 以上で 3 バイトになる（2 バイト目の上のビットが続きの印）。これで残りの 3 枚も読めるようになった
- **スプラットの 4 つの値**: どれも 0.05 刻み。手元のタイルのスプラットを形・色・まわりと比べた（法線は約 60 万枚、ズームごとの比較は約 600 万枚）
  - 2・3 番目は八面体で詰めた法線。三角形の面の向きと内積の中央値 0.996（刻みの粗さの範囲）で一致する。13% は面の裏向きで、空の開けた側を向くものが多い
  - 4 番目（0〜3.15、63 段で張り付く）は、上に重なるスプラットが多いほど小さく、下に多いほど・色が明るいほど大きい（タイルごとの順位相関 −0.35・+0.23・+0.40）。木の外側や上で 3.15、内側や下で 0 になる。法線の向きとは関係がなく、ズームでも変わらない。遮蔽（空の見え方）の値らしいが、光線を飛ばして求めた空の見え方とは弱くしか合わない（順位相関 0.29。全方向の開いた立体角を円すいの半角にしたものでも 0.16、法線のまわりの開いた円すいの半角でも 0.22）。値の幅が 0〜π なので角度の可能性もあるが、見る向きが法線から この角度より外れたスプラットを消すと、Apple の画面から大きく離れる（似ている度合い 0.97 → 0.93）。色を この値で暗くしても、法線と光の向き（8 方向）で明暗を付けても、Apple の画面には近づかない（色はすでに陰を含んでいるらしい）
  - 1 番目（0.05〜1）は 0.7 あたりが多く、1 で張り付く。形・色・まわりとほとんど関係がなく（相関 0.2 未満）、近いものどうしで少し似る（0.42）。大きなスプラットの多い低いズームほど大きい（1 の割合が z20 で 5%、z13 で 24%）。縁のぼかしの指数と考えると分布は合うが、そう使って Apple の画面と比べると一律の指数より少し遠くなる（上の「スプラットの見え方の合わせ込み」）ので、たぶん違う。不透明度や明るさに掛けても遠くなる。大きなスプラットほど少し大きい（面積との順位相関 0.2 前後）
- **分かっていないこと**: スプラットの 1 番目と 4 番目の値の、Apple の描き方での使い方（手元の Apple の画面 3 枚では、使わない描き方がいちばん近い。今の表示では 4 つとも使っていない。確かめるには、木を近くや横から写した画面や、時刻の違う画面が要る）。見出しの 2 つ目の数の正確な式。海や湖の帯の下側の頂点の印の使い道

## Go 版との照合

Python 版の読み取りが、本物のタイルで Go 版と**ビット単位で一致**することを確かめている（金沢 88 タイル・渋谷 121 タイル、計 209 タイル）。確かめ直すには:

```bash
git clone https://github.com/retroplasma/flyover-reverse-engineering
cd flyover-reverse-engineering
git apply ../flyover-web/tools/retroplasma-2026.patch && rm -rf vendor
go build -o dump-json.exe ./cmd/dump-json
cd ../flyover-web
python scripts/compare_go.py ../flyover-reverse-engineering/dump-json.exe cache/c3m/*
```

パッチは Go 版そのものも今のサーバーで動くようにする（`go run ./cmd/export-obj 36.5722 136.6680 20 4 4`）。
