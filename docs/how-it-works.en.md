# How it works

[日本語](how-it-works.md) | English

This page covers what doesn't fit in the [README](../README.en.md): how the data is fetched and how the globe viewer is built.

## Fetching the data

1. Fetch the **resource manifest** (protobuf) to get the URL of the Flyover tiles (style 15) and the `tokenP2` used for authentication
2. From the **list of height regions** named in the manifest (`altitude-*.xml`), pick the region containing the point. A region's name `Reg_z9_X_Y` is the zoom 9 tile it covers
3. Request tiles by `x, y, z, h`. The URL carries `sid` and `accessKey` (built with AES-256-CBC)
4. Read the **C3M** (the 3D model of one tile). The mesh is compressed with Apple's own variant of Edgebreaker (Huffman codes → CLERS string → corner table → parallelogram prediction to restore vertices and UVs). Images are HEIC
5. Convert Earth-centered coordinates (ECEF) to east/north/up in meters, convert HEIC to JPEG, and export for the browser

Satellite imagery is style 7, and terrain is style 17 (zoom 7 and 11 worldwide, 13 for the US and Europe). The versions are in the style settings of the manifest.

## Globe viewer

### Choosing tiles

- Flyover tiles exist from zoom 13 (about 4 km per tile) to 20 (about 30 m). The viewer (CesiumJS) walks the quadtree down from the zoom 9 regions and picks finer tiles where they look large on screen (over 520 device pixels)
- Intermediate levels are not loaded; only the target zoom's tiles are loaded directly (it used to load every other level and use them as fill)
- It refines quarter by quarter where descendants can fill the quarter. Where they can't yet, or where children have no data (water and such), it draws the parent clipped to that quarter
- Until the needed tiles arrive, the gap is filled with finer tiles already at hand (up to 3 levels down) or coarser ones, so the 3D doesn't disappear while you move

### Loading order

- Up to 48 tiles load at once. More doesn't help, because the network link is already full (on a 50–65 Mbps line, 48 requests reached the limit; 96 only made each tile wait longer)
- Only tiles within the screen are loaded, those nearest the screen center first (like Apple Maps). The angle from the center is measured minus the tile's own extent (a large tile covering the center comes first). Nothing off-screen is preloaded (it used to preload off-screen tiles around the camera, but that added loading and model building and felt heavier than Apple Maps on an iPad). At a search destination, the target zoom is loaded after arriving
- Off-screen tiles are not drawn (their models are hidden)

### Lightening the browser's load

- Nothing is drawn while the view is still (Cesium's requestRenderMode). It draws only when the camera moves, or while something is loading or animating
- While loading, the heavy parts are preparing shaders (translating them for the GPU) and sending images to the GPU. Flyover models are unlit (the photo as is), so Cesium's reflections (the dynamic environment map and IBL) and the preparation for `Scene#pick` are turned off. Once the reflections became ready, they made Cesium rebuild every shader, which ate the first few seconds of loading (74 shader programs → 53)
- The cursor elevation and scale in the bottom bar are only rechecked once a second when neither the camera nor the mouse has moved (reading the depth stalls the GPU)
- The time the globe spends on loading each frame is raised from 5 ms to 20 ms

### Conversion on the server

- The height slabs of a tile are packed into one glb (vertices in Earth-centered coordinates) and kept in `cache/glb4/`
- Vertex positions are packed as int16 and UVs as uint16 (KHR_mesh_quantization; 8 cm steps even on a 4.9 km tile)
- When the browser can decode HEVC with the GPU's dedicated hardware (WebCodecs; Chrome doesn't decode HEVC in software), images of the new Flyover are passed as HEVC instead of JPEG (`?hevc=1`, `cache/glb98_16h/`). A HEIC holds just one HEVC frame, so its configuration (hvcC) and the frame go into the material's `extras.hevc`. The viewer decodes them in a worker (`earth/hevc.js`), uses the luma (Y) and chroma (UV) planes directly as textures of a Cesium CustomShader, and converts to RGB in the shader. HEIC carries no color description, so it is treated as BT.601 full range as the HEIF rules say (the same as pillow_heif; Chrome otherwise assumes BT.709 limited range)
  - Building a glb on the server drops from about 125 ms to 19 ms per height slab (no HEIC decoding, shrinking or JPEG). Decoding in the browser takes about 10 ms per image
  - Images stay at their original size (in WebGL2, textures made from arrays are not enlarged to powers of two) at 1.5 bytes per pixel. With 208 tiles loaded over Osaka, images take 438 MB of GPU memory (754 MB as power-of-two JPEG, 2,885 MB before shrinking)
  - Reading a decoded frame back to the CPU (`VideoFrame#copyTo`) took about 100 ms per image and was the heaviest step. So frames are now received as RGB images that stay on the GPU (ImageBitmap) and turned back into BT.601 full-range Y and UV on the GPU, as textures of the same size and format (drawing into a single-channel R8 texture and generating mipmaps took seconds per image on this PC, so they are drawn into RGBA and copied into LUMINANCE and LUMINANCE_ALPHA). The decoder (VideoDecoder) is also reused instead of being recreated. Loading 107 tiles at Tokyo Station went from about 6.5 s to 3.7 s with the same GPU memory, and colors differ by about 1 level on average. With seasonal colors (`?season=`) the photo colors are read on the CPU, so frames are read back. `?gpu=0` always reads them back
  - Which material's image to use is told by the vertex attribute `_SLAB` (the 4th int16 of the position, which used to be padding). If decoding fails, JPEG is used from then on. Add `?hevc=0` to use JPEG only
- Images are shrunk so that width and height are each the next lower power of two. Cesium enlarges images that are not powers of two to the next power of two before building the downscaled levels (mipmaps), so the 1152–1376 px images common in the new Flyover became 2048 px, about 2.5 times the GPU memory (for 314 tiles loaded over Osaka, images are estimated to drop from 3.6 GB to about 1.0 GB)
- Tiles at the edge of Flyover coverage contain a gray band that joins the flat map (mesh kind 4) and a plane at height 0 (kind 3). On top of the terrain these look like a second layer, so they are left out
- Height slabs split heights relative to the tile size. At zoom 16 and below there is only h = 0 (even for Tokyo Skytree or Denver), so zoom 15 and below request only h = 0, and zoom 16 only h = 0–1
- If numba is available, the heavy parts of C3M decoding (`flyover/_fast.py`) are compiled for speed (0.3 s → 0.06 s per tile in a dense city; the output is bit-for-bit identical to the pure Python version). Decoding runs in parallel in worker processes started at launch. So as not to compete with the browser for CPU, it uses a quarter of the cores (at most 4; each takes 140–190 MB of memory) at slightly lowered priority

### Requests to Apple

- They use HTTP/2 (httpx), with up to 90 concurrent requests on each of 4 connections. Apple takes about 1 second per tile, but the more you run in parallel, the faster it goes (with requests over HTTP/1.1, TLS setup per connection and so on meant waiting about 4 seconds for a response at 32 concurrent requests)
- If a request hasn't returned after 1.5 seconds, the same request goes out again on another connection and whichever returns first is used (and a third one 3 seconds later if still waiting)
- Each request gives up after 10 seconds. A connection that has stalled as a whole (nothing returned for a while) is reopened (before this, some requests waited 60 seconds)
- Terrain and satellite imagery are fetched on a connection separate from the Flyover tiles. While 16 or more Flyover tiles are being fetched, however, they are limited to 4 at a time. The link fills up either way, and much of the ground imagery is hidden under the 3D city, so doing the city first makes the view look good sooner

### Terrain

- Terrain is a 16-bit PNG. The 12 bytes appended after the end of the PNG (IEND) hold a float32 base height and scale (0.25): height = base + value × scale
- Heights are ellipsoidal, the same as Flyover, and the base differs per tile (miss it and inland terrain ends up hundreds of meters too low)
- The server converts the terrain into Cesium's geographic tiles
- EGM96 geoid heights (2.7 MB fetched from the PROJ data files on first run) are used for sea level where there is no terrain tile, and for the elevation shown on screen

### Atmosphere

- The sky color and the haze in the distance are drawn with Eric Bruneton's [Precomputed Atmospheric Scattering](https://github.com/ebruneton/precomputed_atmospheric_scattering) (BSD license). The computation itself (`flyover/earth/atmosphere/functions.glsl`) and the atmosphere parameters are unchanged from the original demo. Google Earth's atmosphere is by the same author (confirmed from the comments of the shaders inside the web version's WebAssembly; no Google code is used)
- **Precomputation**: the scattering for each sun height, view direction and altitude goes into a 3D texture (256×128×32), and the atmosphere's transmittance and the sky light reaching the ground into 2D textures. The original `model.cc` is ported to WebGL2 (`flyover/earth/atmosphere.js`); it runs in a separate WebGL inside a worker, and the results are read back and uploaded to Cesium's WebGL. WebGL2 has no geometry shaders and cannot switch blending per output, so 3D textures are drawn layer by layer, and overwritten and accumulated outputs are drawn separately. About 4 seconds on this PC
- **Rendering**: a Cesium post-process (a full-screen shader) finds the distance to each point from the depth and applies "original color × transmittance + light scattered by the air" to the photo. The photo color is treated as a value on the same brightness curve as the sky (an ACES approximation) and converted back before mixing, so nearby it stays the photo, far away it approaches the sky color in the same direction, and there is no seam at the horizon
- **Look (`?look=`, the button, the G key)**: `apple` is Apple Maps' own look with no atmosphere processing (the same as before the atmosphere: Cesium's sky, photos as they are). `google` uses the color-matching values below. The atmosphere textures are computed in `apple` too, and switching only adds or removes the post-process. It starts as `apple` on first open, and the choice is remembered in the browser
- **Color matching (`google`, with atmosphere)**: **The current defaults aim for realism** (changed in November 2026): aerosol × 3, sky and haze color R 1, G 1, B 1.1, and the amount of air applied to the photo is close to the computed value up to the tens of kilometers seen over a city (0.4 far away, 2.5 times nearby, distance scale 100 km: 0.94 at 10 km, 0.84 at 30 km; from space it is 0.4, since at 1 the whole ground turns a pale blue). As on a clear day over a city, the distance turns a whitish grey and the mountains fade into the sky. When the amount of air applied to the photo is changed, the added air light and the fading of the colors are changed together (the transmittance t^a for a times the air, and the matching air light S × (1 − t^a) / (1 − t)). Before, only the added light was changed, so weakening the distant haze made the distance sink dark and blue instead of fading into bright haze. What follows is how the earlier values, matched to Google Earth, were chosen (`?haze=0.5&balance=0.95,0.97,1.3&aerialNear=3&aerialKm=2` gives the earlier look). Tuned by comparing the sky and mountain colors with Google Earth at the same place in Toyama. With the original demo's values (aerosol × 1, exposure 10, curve 1 − exp(−x)) the sky is whitish and distant mountains are too hazy. The physically computed sky is less blue than Google Earth's, and no curve matches the red-to-blue ratio, so the sky and haze are multiplied by a color (R 0.85, G 0.88, B 1.8). Google Earth's sky differs between scenes (the Toyama image is a deeper blue than the Tokyo one) and no single color fits both, so this is in between. Lowering green too much makes the sky near the horizon in Tokyo purplish. When comparing, match the field of view to the value in the Google Earth URL (`35y` is 35° vertically). The air light added to the photo depends on the distance: 0.4 far away and stronger nearby (0.4 × (1 + (n − 1) × exp(−d / 2)) at d km). Comparing the same buildings, Apple's photos are nearly neutral (blue minus red is +1 to +6) with brownish ground, while in Google Earth even a black building about 2 km away is a blue 39, 46, 84. This comes not from the photo but from a strong blue haze added from close range. At the sky's strength (1) the haze is too weak nearby and distant mountains become too white and blue. **The defaults are milder**: the values matched to Google Earth (color 0.85, 0.88, 1.8 and n = 6 nearby) looked too blue, so the color is R 0.95, G 0.97, B 1.3 and n = 3 (to match Google Earth, use `?balance=0.85,0.88,1.8&aerialNear=6`). The "divide by the color of a white surface at sunset" balance described in Google Earth's shader comments was also tried, but with these atmosphere values the white surface at sunset is bluish, and blue got weaker instead
- With the values matched to Google Earth, colors at the same place with the same field of view (against Google Earth): in Toyama, top of the sky 125, 189, 241 against 110, 162, 235 and foot of the mountains 80, 121, 187 against 86, 131, 189; in Tokyo (Shinjuku), top of the sky 151, 205, 242 against 149, 200, 248 and just above the horizon 201, 223, 244 against 200, 225, 251. Because blue is boosted, the sky toward the sun turns purplish in the evening (`?light=evening`)
- Depth is stored logarithmically. Cesium's `czm_windowToEyeCoordinates` lacks the precision because of the far plane (10 billion m) and gives distances of almost 0, so the distance is recovered from the logarithm directly
- The sky is laid underneath where nothing is drawn (opacity 0). Layering by opacity instead of depth keeps splats (translucent, no depth written) and anti-aliased edges from being erased by the sky
- The Earth is an ellipsoid but the atmosphere is a sphere with a radius of 6360 km. The camera is placed on that sphere at its height above the ellipsoid below it, and each point is found from its direction and distance from the camera
- The sun is daytime (azimuth 150°, height 45°). If `?light=` has a sun, its direction is used; at night the sun is set. `?atmo=0` turns this off (Cesium's sky). For tuning: `?exposure=` (default 6), `?haze=` (aerosol multiplier, default 3), `?balance=r,g,b` (sky and haze color), `?aerial=`, `?aerialNear=`, `?aerialKm=` (for the air light added to the photo: the multiplier far away, how many times stronger nearby, and that distance scale; defaults 0.4, 2.5, 100), `?tone=exp` (the original demo's curve)

### Other

- To get around the browser's limit on concurrent connections (6 per host), Flyover, satellite and terrain tiles are spread across different loopback addresses (127.0.0.2–127.0.0.17)
- Place search is relayed to OpenStreetMap's Nominatim

## The WebGPU viewer

`gpu.html` draws directly with WebGPU instead of CesiumJS. It chooses tiles and draws the atmosphere the same way as the CesiumJS version, and is made lighter in these ways (`flyover/earth/gpu-*.js`):

- **Choosing tiles**: Not every frame. It chooses a slightly wider area than the screen (1.2 times) and chooses again only when the camera leaves that margin, when the distance to the ground changes by 5%, when a tile arrives (after 0.1 s), or after 0.5 s
- **Photos**: The new Flyover's HEVC is decoded by the GPU's video hardware, and the decoded frames are read directly with `importExternalTexture` into brightness (Y) and color (UV) textures. JPEG and PNG are opened with `ImageDecoder` and copied to the GPU from a buffer created mapped (ground JPEGs stay as Y, U and V). In both cases mipmaps are made on the GPU and compressed to BC4 and BC5 (about half the photo memory)
- **Stutter while loading**: GPU commands for photos are sent once per frame, and up to 8 ground tiles and 4 Flyover models are put on the GPU per frame. HEVC is decoded one at a time (decoding several at once clogged the GPU side and froze the screen for around 100 ms). `queue.writeBuffer`, `writeTexture` and `copyExternalImageToTexture` can wait for tens of ms to over 100 ms per call while drawing, so they are not used for large data
- **Drawing**: While the camera moves, MSAA is 1x and the view is drawn at 0.75 of the width and height (56% of the pixels) and stretched to the screen. 0.15 s after it stops, the view is redrawn at full size with 4x MSAA (the cost follows the pixel count closely: at 1600×1000 while moving, a frame took 27 → 25 ms in daytime and 40 → 33 ms in the night view).
- **Haze table**: The distant haze (`aerialAt`) used to be computed per vertex, and with millions of vertices it cost about 17 ms of GPU time (compared with `?look=apple`). Now a compute shader works out the haze once per frame for 32×32 view directions and 32 distances from the camera (30,000 points; distances up to the visible horizon + 200 km, evenly spaced in the square root), and vertices look it up (GPU time while moving at 1600×1000: 45 → 34 ms). It is not used when the camera is above 30 km (from outside the atmosphere the haze changes abruptly where rays enter it and the table shows bands; few vertices are drawn from high up). Tree splats are blended with Weighted Blended OIT (McGuire and Bavoil 2013), as in the CesiumJS version
- **Reading tiles in the browser (`?raw=1`, `?c3m=1`)**: The server (`/api/r3d/<z>/<x>/<y>.bin`, `/api/c3m/<z>/<x>/<y>.bin`) only passes on the R3D or C3M of each height slab as received from Apple, and browser workers (`earth/c3m.js`, `earth/r3d.js`, JavaScript ports of the Python readers) expand the meshes and splats. They build the same layout as a glb in memory, so from there it takes the same path as a glb (seasonal colors included). Tiles without R3D, or with any slab that can't be read, use C3M (as the server does). The images (HEIC holding one HEVC frame) are decoded on the GPU. R3D's sun-exposure and glass maps are monochrome (4:0:0) HEVC, which Chrome's WebCodecs doesn't accept (`hvc1.4…` is unsupported), so `?light=` falls back to the normal glb
  - Speed (on the same 40 files): C3M mesh expansion runs at about the same speed as the Python version with numba (3–4 ms per file). The server's glb build (about 27 ms per height slab, mostly turning HEIC into JPEG) goes away; the browser spends about 3 ms per slab plus the HEVC decode on the GPU. For R3D, reading takes 12 ms (7 ms in Python with numba) and building the glb layout 15 ms in total (the server's glb build also takes 15 ms)
  - The glb content matches the server's (positions, UVs, triangles, splat colors and capture time compared). Only the splat order can swap two splats of almost the same height (the dot product rounds differently from numpy)
  -  Apple's responses have no `Access-Control-Allow-Origin` and the URLs need an auth string, so the browser cannot fetch from Apple directly (a relay is still needed)

URL options to compare with the earlier ways: `?reuse=0` (choose every frame), `?hevcframe=0` (receive HEVC as ImageBitmap), `?bc=0` (no compression), `?imgdec=0` (copy JPEG through ImageBitmap), `?batch=0` (send commands one texture at a time), `?hevcw=3` (decode 3 HEVC at once), `?msaa=1`, `?scale=1` (do not shrink while moving), `?lodpx=520` (size at which tiles are refined).

## What had changed on the servers by 2026

Since the original, retroplasma/flyover-reverse-engineering (archived in 2021), the following had changed. This project is adapted to them.

- The manifest's file location (`cache_base_url`) is now empty → use `https://gspe21-ssl.ls.apple.com/`
- The per-region index C3MM version 1 (style 14) now returns 404 (version 2, fetched by tile coordinates as style 52, does respond, but its format is not decoded) → skip the index, request the area's tiles and height slabs directly, and skip empty responses (the new Flyover has a separate index, style 100, which is decoded and used; see "Index" below)
- The 5th byte of C3M (the version) went from 3 to 7 → it reads fine with the version 3 reader
- Images changed from JPEG to HEIC (image format 13)

Also, the original tool picked the region "whose center is closest", which picks the wrong one where regions overlap, as in Tokyo (Shibuya returned no tiles at all). This project picks regions by the tile number in the region name `Reg_z9_X_Y`.

The authentication steps and `tokenP1` are the same as the Look Around implementation in [sk-zk/streetlevel](https://github.com/sk-zk/streetlevel) (which also comes from retroplasma). retroplasma's setup downloads the Xcode simulator SDK (about 2 GB) to extract `tokenP1`; that isn't needed here.

## The new Flyover (style 98)

The manifest requested as iOS 27 lists the new Flyover tiles (style 98). Start with `python scripts/earth.py --r3d` to use them at every zoom; only tiles without the new Flyover or that can't be read are filled in with the old C3M (so the scene doesn't switch between old and new data as you zoom). The reader is `flyover/r3d.py`.

- **Fetching**: Tile numbering and height slabs are the same as C3M. Request `?style=98&v=<style 98 version>&region=<region>&x&y&z&h` (`v` is the style 98 version, not the region's version)
- **Gaps in height slabs**: Unlike C3M, some tiles skip 4–7 above h = 0–3 and continue at 8–15. At Azabudai, 0–3 reach about 150 m above the ground, 4–7 are empty, and 8–15 go up to about 300 m (the upper halves of Mori JP Tower and Tokyo Tower; Tokyo Tower's upper lattice is mostly splats). Some tiles have 0–3 all empty and data only at 12, 14 and 15. Nothing was found above 15. Many other tiles do continue at 4–7 (no local tile had data in both 4–7 and 8–15). So at zoom 17 and above, if h = 3 has data or 0–3 are all empty, 4–15 are requested together, and the next 4 are requested while the last one has data (`fetch_heights` in `flyover/earth.py`; C3M still goes 4 at a time). Before, fetching stopped at the empty 4–7 and everything above 120–150 m was missing
- **File**: A container starting with `3D 96 59 2E` holds triangle splats (part 1) and a textured mesh (part 2). The mesh coordinates become Earth-centered coordinates (ECEF) with the 3×3 rotation and translation in the first entry of part 2. Textures are the image entries of part 2 (entry 3); a tile with several textures has that many entry 3s (3,317 of the 36,695 cached tiles, mostly places such as Fukuoka where the old Flyover's shapes were carried over). The first HEIC in each is the texture
- **Splats**: Trees and the like are triangle splats, not mesh (a park tile has a small mesh and close to 20,000 splats). Each has 3 vertices, a color and opacity, and 4 more values (see "The 4 splat values" below). Apple draws them denser toward the inside of the triangle, fading out at the edges. In the glb they are semi-transparent triangles with vertex colors (RGBA), with a shared small image that gets more transparent toward the edges, for a similar look (it doesn't match Apple's drawing pixel for pixel). Because they are semi-transparent, they are drawn from lowest to highest (unless drawn back to front, near colors get painted over by far ones and look muddy; the view is usually from above, so height order is enough)
- **Matching the splat look**: compared with 3 screenshots of Yumeshima (the forest inside the Grand Ring) from Maps on iOS 27. Feature matches between the screenshot and the export gave Apple's camera position and direction (PnP; the vertical field of view is 30° in every screenshot, median error 0.5 px), the same view was drawn, and brightness was correlated over the trees. Unsorted: 0.83–0.87. Lowest first: 0.91–0.95 (the same as re-sorting back to front for each view). Of edge-softness exponents 0.25–3, 1.5 is closest (0.95–0.97); using splat value 1 as a per-splat exponent is slightly further than a uniform 1.5 at every scale
- **Compression**: The content is the same Edgebreaker variant as C3M, split into streams and packed. Each number sequence is packed per "lane" with a bitmap (1 for the next value, 0 to repeat the previous value or look up a table) and Huffman codes (Apple's own table format)
  - **Shape**: The C / other bit per triangle and the 2-bit kind of the others are rebuilt into the old C3M single bit stream, and `edgebreaker.py` turns it into triangles
  - **Positions**: An integer per vertex × a step. It holds the difference from a parallelogram prediction while walking the triangles breadth first
  - **UV**: 4 bits per triangle mark UV seams. UV numbers are assigned depth first, bounded by seams, and the values are restored with a breadth-first parallelogram prediction bounded by seams. The unit is a quarter texel
  - **Lane directory (J)**: Bits for the lanes in use, a 2-bit kind per lane (a 2m + 6 bit field for m lanes), and a length and fill mark per lane. The kind says what changes for the next lane: if its high bit is 1, the next lane's length is written (otherwise it is the same); if its low bit is 1, 1 byte with the next lane's fill mark is written (otherwise the fill is the same). The first lane's mark sits at the byte boundary after the kind bits (when m leaves a remainder of 1 when divided by 4, it doesn't fit in the field and there is no mark). Marks: 0 = raw bytes, 1 and 4 = repeat, 2 and 5 = table lookup, 3 and 6 = signed differences. 1–3 are lanes of 8-bit values and 4–6 lanes of 16-bit values (true for 4,320 of 4,323 local lanes; the rest are 16-bit lanes whose values happen to be 255 or less)
  - **Splats**: BYET blocks for the position (XYZ) and 8 attributes. The origin is 4 bytes per component, or a packed form of that. One packed form is itself a small BYET (the bytes of the int as lanes, the components as values)
  - **Normals**: Spherical coordinates in 2° steps (not read now, since the view has no lighting)
- **Speed**:
  - The heavy loops (Huffman codes, lane filling, the 3 walks, prediction replay) run in numba. One tile takes 20–150 ms, 5–13 times faster than plain Python.
  - Reading the Huffman code tables and expanding the triangle connectivity (CLERS) also run in numba. Reading one height slab of the new Flyover went from about 36 ms to 23 ms (on 4,838 local tiles the output is exactly the same as before).
  - Each Huffman envelope is one numba call (read the table, check its shape, build the lookup table, read the body). The body is read by keeping a bit buffer and peeking a code length at a time, instead of one bit at a time. Splat decoding went from about 3.6 ms to 2.1 ms per tile, and reading one height slab from about 11.5 ms to 8.5 ms (on 1,500 local tiles the output is exactly the same as before).
  - So that broken data doesn't crash or hang the process, index ranges are checked before handing data to numba, the corner-table walks run with index checks (`boundscheck`), and loops have an upper limit.
  - In building one tile, decoding the image (HEIC, 100–150 ms) is the heaviest part.
  - The new Flyover is often not yet cached on Apple's delivery servers, so the first fetch of a tile takes 1–2 seconds to respond (tens of ms from the second time; it is also kept locally in `cache/r3d/`).
  - New Flyover tiles at z16 and below are large, around 1 MB each, so in a new place the distant view takes 1–2 seconds to appear. Tiles whose fetch times out are not filled with C3M; the viewer fetches them again later.
- **Checking**: On the 29 Tokyo tiles whose decoding by Apple itself (exported from the iOS 27 simulator) is published, the mesh triangles, positions, UV numbers and UV values, and the splat vertices, colors and attributes all match bit for bit
- **Where the format comes from**: Apple doesn't document it. It was worked out from the data, using the prose of [nmt3325/apple-maps-r3d-research](https://github.com/nmt3325/apple-maps-r3d-research) as clues (its code was not read, since it has no license). The reference data used for checking is from the same repository
- **Lane filling**: Decided by the mark in J (on about 150,000 splat lanes in the local tiles, the mark and the filling worked out from the data agree every time). For lanes without a mark: where the prediction is right the bit is 0, so with the right filling a literal never equals the prediction, and that is how it is chosen
- **Mesh field section**: int32 values for the face count, the corner pairs (va, vb) glued in advance, the vertex count and so on. The fields are laid out as 4 bytes each, and the byte string is packed with a table lookup, using each field's 4-bit mark (which bytes are written) as the bitmap (the same as mode 4 of the origin packing: an unwritten byte is table[previous byte], and each written byte sets table[previous] = it). When the section starts with 0C, that is packed again with a repeat bitmap. Every field in the local tiles reads correctly this way
- **Header numbers and small tiles**: The two numbers in the header and the two numbers after XYZ take 1 byte when small. They are all sizes of working space for decoding: a count n turned into "n if under 64, otherwise n + (floor(n / 64) + 1) × 64". The first header number comes from the triangle count and the two after XYZ from the UV count (all 2,487 surveyed tiles match; the second one after XYZ is occasionally a little larger). The second header number is the same formula applied to the byte length of the C bits (triangle count / 8, rounded up) plus the byte length of the non-C kinds (non-C triangle count / 4, rounded up) (all of another 2,489 tiles match). They are not used for reading. In small tiles the seam block, and in large low-zoom tiles the per-triangle C bits, are stored unpacked or as a 1-lane BYET
- **Version 1 container**: Rare in upper height slabs. It has no part and item framing: from byte 16 come 12 doubles for the rotation and translation, then the splats (starting with `D1 22 C9 07`), the mesh (starting with `E1 21 66 24`) and the image HEIC. The contents have the same form as version 2 and read the same way
- **Choosing the texture**: The "per-chart number" block of the mesh section gives the texture index for each UV chart (a group bounded by seams, numbered in traversal order). It is a list of int32: stored as is when small, otherwise as a 4-lane BYET (the value is lane 0, or lane 1 when lane 0 is absent). It is empty when there is one texture. UV values are in units of a quarter pixel of that chart's texture. On Fukuoka tiles this matches the material split of the C3M for the same place, down to the triangle counts (before, only the last texture was read, so such tiles had their images pasted wrongly)
- **Bands and planes at the edge of coverage**: A texture whose image entry has item 13 (value 1 or 2) joins the Flyover to the flat map at the edge of coverage, like mesh kinds 4 (edge band) and 3 (flat plane) of the old C3M. Value 1 is a band along the terrain with a coarse photo whose parts without imagery are uniform grey. Value 2 is a flat plane, often a pure black 16 px square image (near 0 m height in Paris). They are in z13–17 tiles at coastal and inland edges of coverage (such as west of Kameoka). As with the old C3M, they are left out of the glb (otherwise a grey band and black planes appear at the edge of coverage). They were first misread as water fills and tiled (on 6,000 local tiles their UVs never go outside 0–1). The extra block after the XYZ block (a 1-bit mark per vertex) marks the lower vertices of a sloping band that runs 25–57 m outward and 66.6 m down from the edge of the sea or a lake (every marked vertex is on the mesh boundary, belongs only to water-texture triangles, and sits at one shared height). The band is a slope with the water texture, apparently hiding the gap at the border with the neighboring ground. What the mark is used for (hiding the lower edge, or water depth) is unknown
- **Seams with the same UVs on both sides**: These occur only in coastal z13–14 tiles (4 of 2,487 surveyed), always on edges between land-photo triangles. They are short lines of 1–2 edges, with one end on the coastline (the mesh boundary) and the other stopping inland. They are lines where the surface was cut open to make the photo UVs, but since the photo is applied from straight above, both sides apparently ended up with the same UVs. UV numbering splits them like ordinary seams, but UV value prediction crosses them
- **How much can be read**: All 37,542 cached tiles can be read. The last 12 unreadable tiles (coastal z13–14) came from following the wrong order when predicting UV values. Coastal tiles have edges that carry a seam mark although both sides have the same UV numbers. UV value prediction crosses an edge when both sides have the same UV numbers, not by the mark (stopping at the mark shifts the prediction references, and the photo UVs go far out of range). After the fix, the photo is applied the same way as in the C3M of the same place. Coastal tiles of the same layout that could already be read, but whose photo UVs stuck out a little, had the same misreading
- **Drifting positions and large tiles**: In position prediction, the midpoint of the first triangle of a piece also becomes the previous prediction (it did not before). Positions drifted after pieces with only 3 vertices: 9 tiles could not be read, and 153 were read partly shifted. After the fix, tiles that carry over the old Flyover's shapes match the C3M in both positions and UVs within the quantization step. Also, the chart count (a small number) takes 3 bytes from 8,192 up (the top bit of the second byte marks the continuation). This made the remaining 3 tiles readable
- **The 4 splat values**: all in steps of 0.05. Compared against the shape, color and surroundings of splats in the cached tiles (about 600,000 for the normals, about 6 million for the per-zoom comparison)
  - Values 2 and 3 are an octahedral-packed normal. It matches the triangle's face normal (median dot product 0.996, within the quantization). 13% point to the back of the face, mostly toward the open side
  - Value 4 (0–3.15, piling up at step 63) is how much sun the splat gets (near π in the sun, 0 in shadow). It is the same quantity as the grey image attached to the mesh texture (item 6 below). Casting shadows over a height map built from the mesh and splat heights, with the sun direction varied in 15° steps, matches the value best at azimuth 150° (south-southeast), elevation 35° around Tokyo Station and at azimuth 195°, elevation 45° around Nagoya Station (correlations 0.38 and 0.37), and in both places that is the same direction that best matches the item 6 image of the same area. This is why it is large on the outside and top of trees, 0 inside and underneath, and larger for brighter colors (correlation 0.3–0.4). It was earlier taken for occlusion (how much sky is seen), but it matches sky visibility only weakly (rank correlation 0.29). Darkening colors by it does not get closer to Apple's screenshots (the colors already include the shading; Apple apparently uses it when redrawing with a different light direction)
  - Value 1 (0.05–1) is mostly around 0.7 and piles up at 1. It barely relates to shape, color or surroundings (correlations under 0.2) and is somewhat similar between neighbors (0.42). It is larger at low zooms, where splats are big (the share at 1 is 5% at z20 and 24% at z13). It seems to correspond to the other grey image of the mesh (item 8): both have a bell-shaped distribution and relate neither to brightness nor to the sun value. Item 8 is larger on horizontal faces (mean 0.60 on roofs and ground, 0.35 on walls) and small at windows, so it looks like a surface-quality (roughness-like) value, but this is not confirmed. Used as an edge-softness exponent, opacity or brightness, it moves away from Apple's screenshots
- **Index (C3MM version 2, style 100)**: An index says which height slabs of which tiles have data. Requesting `?style=100&v=<version>&x&y&z` with a zoom 9 tile returns the index for zooms 13–16, and with a zoom 13 tile the index for zooms 17–20 (no region). The reader is `flyover/c3mm.py`
  - **Container**: `C3MM`, version 2, the number of sections. Each section has a kind, a length, a compressed flag and the original length, and its body is LZMA (after a header of `5D 00 00 10 00` and 8 `FF` bytes)
  - **Tree**: For each root (the tiles of that zoom: x, y, height slab), the nodes follow depth-first. A node is 16 bits, 2 bits for each of 8 children (the low byte is the 4 in the lower half of the height, the high byte the 4 in the upper half). The low bit means "this child has data", the high bit "near the edge of the covered area" (a band about 2 tiles wide, plus the tile just outside)
  - **Height slabs form an octree**: A child's height slab is parent × 2 + (1 if in the upper half). This is why slabs continue at 8–15 above 0–3
  - **Height ranges**: Each root stores its lowest and highest point (ellipsoidal height) in 8 bits each, and each child stores, in 4 bits each, how far to narrow the parent's range from below and above in steps of 1/16 of that range (the actual heights of 148 out of 150 local tiles fit within 0.5 m)
  - **Check**: Compared with the "present / absent" state of 10,710 tiles fetched earlier. Every slab that disagreed was asked from the server again (102 slabs, after widening the comparison to 11,455 tiles). 90 were stale caches from an older version and 12 were slabs left on the server that the index does not list (in Toyama, h = 2 and 3 hold shapes overlapping the listed slabs at the same height; Apple's app follows the index and does not use them). The index was never the one that was wrong
  - **Use**: The server and the exporter request only the slabs in the index (`fetch_r3d` in `flyover/earth.py`; for 8 tiles at Nagoya Station, requests to Apple went from 56 to 22). When the index cannot be fetched, slabs are probed in order as before
  - **Section 9 (data generation)**: 1 or 2 per root. Tiles under a root with 1 are repackaged old Flyover shapes, with no splats and no lighting images (all 1,500 checked; Paris, for example). 2 is new data. Some indexes have no section 9
  - **Section 8 (data batch number)**: A number per root (97–944 seen). Neighboring roots share a number, and one index mixes several. The largest number equals the current manifest version (944), but it is not a version number (tiles that existed at version 731 and have not changed carry 891; requesting with that number as `v` gives 410)
  - **Unknown**: How the section 8 numbers are assigned, section 4 (5 bytes `02 00 10 0D 14`, only in the zoom 9 index; it reads as two index levels, one down to zoom 16 and one per zoom 13 tile down to zoom 20, but every index has the same value so this cannot be checked), and what the edge mark is used for
- **Grey images next to the texture**: Besides the texture (item 1), the image section holds two grey images at half the width and height (items 6 and 8), `03` (item 3) and 12 bytes (item 5: an f32 of 3.139 or 3.141 and two zeros)
  - **Item 6 is a map of sun and shadow**: a nearly black-and-white image, white in the sun. Casting shadows over a height map built from the mesh, with the sun direction varied, gives a correlation of 0.80 at azimuth 150°, elevation 35° around Tokyo Station and 0.79 at azimuth 195°, elevation 45° around Nagoya Station (−0.2 for directions that do not fit). Around the Empire State Building in New York it is 0.61 at azimuth 135°, elevation 55° (splat value 4 also fits best one step away, at azimuth 120° and the same elevation). Its correlation with the photo's brightness is 0.7–0.8. Multiplied by the item 5 number (close to π) it spans the same range as splat value 4 (0–π), and it fits best at the same sun direction, so it is the same quantity
  - **Item 8 is a glass map**: unrelated to brightness and to the sun map (correlations under 0.1), and bright on horizontal faces (correlation with how much the face points up: 0.49). It does not match the amount of light from the sky (0.06). Next to the photos of Osaka building walls (zooms 18–20), glass curtain walls are almost black (even glass that looks light teal in the photo), walls with a grid of windows show each window as a dark cell, and frames, outer walls, roofs and roads are light grey. Its correlation with photo brightness is 0.17 (60 textures). It seems to be surface smoothness (how reflective it is) and to correspond to splat value 1. The night view uses it for window lights (`?light=night`)
  - **Items 14 and 15 of edge bands**: A band texture (one whose item 13 is 1) carries two 256 px square black-and-white images. Item 14 is a sharp mask that is white where the coarse photo has imagery, and item 15 is the same blurred (apparently to blend only the part with imagery into the map; unused here since bands are not drawn)
  - All of these look like material for relighting. The viewer's `?light=` uses item 6 (see "Changing the lighting" below); the night view also uses item 8
- **Clouds (WebGPU viewer, `gpu-clouds.js`)**: a WGSL port of the cloud shaders of [takram's three-geospatial](https://github.com/takram-design-engineering/three-geospatial) (MIT; @takram/three-clouds, a three.js post effect) (`?clouds=` sets the amount, default 0.3). A weather texture (512 × 512, three channels: low clouds 0.75–1.4 km, clouds above 1.0–2.2 km, cirrus 7.5–8.0 km) is mapped onto the globe with cube-sphere coordinates, 100 times per face; a shape noise (128³) and a detail noise (32³) erode the density into cloud shapes, distorted by a turbulence noise. Lighting adds the optical depth from a 2-step march toward the sun and from a Beer Shadow Map (distance to the cloud front seen from the sun, mean extinction, maximum optical depth), approximates multiple scattering with 8 octaves (Oz), and adds skylight and ground bounce. The noise is generated by compute shaders at startup (takram's procedure; the shape noise is split into 16 slices per frame since it is heavy). Differences from takram: lengths in km; the atmosphere uses this viewer's tables (gpu-atmo.js); the cube-sphere frame is rotated so Japan (36°N, 138°E) is at a face centre (otherwise a cube corner sits over Japan and the pattern breaks at face seams); one shadow map covering 100 km around the camera (rebuilt when the camera moves 1 km); haze (an exponential height fog integrated analytically, thicker at cloud amounts of 0.2–0.4) and light shafts (the length of the view ray inside cloud shadow, counted from the shadow map, whose air light is removed; the atmosphere lookups follow Eqs. 17 and 18 of Bruneton's paper) are computed in the cloud pass for the sky (the fraction of sky light removed by the shafts goes into the coverage used when compositing onto the sky) and in the haze table for the ground and buildings; the first step is capped at 1 km (it is 1% of the distance to the ray start, so from space it exceeded 5 km and skipped the cloud layer). The drawing pipeline is this viewer's: rendered at 1/3 resolution, accumulated while still, blended with the previous frame shifted by the cloud distance while moving (temporal reprojection), and composited into the sky; above 600 m, clouds in front of the ground and buildings are drawn separately and composited. The ground, buildings and trees receive cloud shadows from the shadow map. The weather texture repeats the same pattern, so from space the clouds look like fine scattered speckles
- **Changing the lighting (`?light=`)**: The server turns item 6 into a grey JPEG in the glb material's occlusionTexture and puts splat value 4 (the sun value) into the low 6 bits of the 16-bit opacity (`flyover/glb.py`). The viewer brightens the shadows to remove them and lights the result again with a different sky and sun (`morning`, `evening`, `cloudy`, `night`). Shadows in the photos are about R 0.10, G 0.15, B 0.17 of the sunlit brightness (linear values, median of 67 photos; bluish because only the blue sky lights them). Face directions come from the change of position across the screen. The sunlit parts of the photo are brighter on walls facing the sun and darker on faces it hits at a slant, so when removing the original light the viewer also divides by the face's angle to the sun at the capture time (the cosine to the sun over the sine of the sun height, so flat ground stays 1; limited to 0.25–2 against wrong face directions). That sun comes from each tile's capture time (zoom 20; other tiles ask `/api/captured` for the zoom 20 tile at their centre) and place; where no time is known the old rule (1 everywhere) is used. Shadows cast by buildings are not created anew. `check` shows item 6 as it is. `?sun=azimuth,height` (degrees) sets any sun. The WebGPU viewer also applies the same light to the ground tiles (the photo's shadows are not removed; the ground is taken as sunlit)
  - **Forest ground (WebGPU viewer)**: mesh pixels with vegetation colours (red or green stronger than blue, both green trees and autumn leaves) do not have their shade removed. In the new Flyover the forest-floor mesh is a photo of the canopy taken from above, largely in shade from the trees; removing it brightened it 6–10×, so it looked brighter than the tree splats drawn on top. Shaded walls and roads photograph bluish from skylight, so their shade is still removed
  - **Night view (`night`, WebGPU viewer)**: brightness is matched to night gameplay footage of GTA6 (screen median 0.04–0.07, top 1% at 0.6–0.8, 1.4% of city pixels above 0.75; previously the median was 0.16 with 5% bright pixels and clipped lights). The default lit-window fraction is 0.22 (was 0.7), distant wall light specks are one per 450 m² (was 150 m²), and the overall light gain is 0.85 (was 2; `?nightGain=` changes it). The atmosphere tables only go down to a sun height of -11.5°, so a set sun still leaves brownish twilight light in the sky and haze; at night it is cut to 20%. The night sky and the light-lit haze are navy-tinted, and a colour grade adds navy only to dark screen values (below 0.1), so shadows and walls are bluish black instead of dull grey. windows are lit. When the viewer adds `night=1`, the server puts the glass map (item 8) into the green channel of the sun-mask JPEG (4:4:4 without chroma subsampling; the glb grows by about 5%; `cache/glb98_20hn/`). A night photo of Umeda was the reference. Only walls (faces whose upward component is below 0.3–0.6) where the glass map is dark are lit. As in offices, lights come on in rows: per 3.8 m floor, in 8 m runs along the wall. Each building (30 m square cell) gets its own share of lit windows and its own color (white LED, or the warm white of hotels and homes), with an occasional warm bulb. A window grid (a dark band between floors and frames every 1.5 m) is added and averaged out where it is too fine in the distance. Some of the photo's window pattern is kept. Positions are measured east/north/up from a 20 km grid point, whose offset to the camera is computed on the CPU in double precision (in Earth coordinates, f32 only resolves 0.5 m, too coarse for the window grid). Everything is chosen from the position on Earth, so it stays the same across tiles and zooms. The view from above follows videos taken from the window while landing at Haneda and Itami (almost black between lights, roads as an orange web, residential areas as clusters of warm white points, rivers and parks black). Distant walls get window points (one per 150 m², mostly warm white), and flat faces on roads get street-light points (one per 60–70 m²; brighter on wider roads) and a faint glow on the pavement; roofs get none. The roads are OpenStreetMap data: the server takes OpenFreeMap vector tiles (zoom 14, the OpenMapTiles transportation layer), keeps them in `cache/osm/`, and draws the roads in a Flyover tile's area, seen from above, as a 256 px square image (`/api/roads/z/x/y.png`, `flyover/osm.py`; red is road, with width and brightness by class, green is elevated; tunnels, footways and railways are left out; blue is floodlit ground: industrial land from the landuse layer (port wharves and factory yards) and airport aprons from the aeroway layer). The viewer lights the flat faces of the tile that lie on a road seen from above, limited to ground level (up to 8 m, relaxed by 2–3 pixel sizes in the distance) unless elevated (so the edges of roofs next to roads stay dark). Flat ground-level faces in the blue areas get floodlighting: an orange glow and about one bright point per 900 m², like high-mast lamps (ports look like orange patches in aerial night photos). Main roads (secondary and above) get orange sodium-lamp lines and points; small streets get mostly white LED points (aerial night photos show main roads as orange lines and residential areas as a carpet of white specks). Since this is decided from above, the decks of elevated expressways light up and slopes are handled. Ground level is the height 2% from the bottom of the tile's vertex heights (`lowGround`; coarse tiles have skirts hanging tens of meters down to hide seams, so vertices more than 30 m below the median are dropped; the tile's center point is at ellipsoidal height 0 m, not on the terrain). When the road image cannot be fetched, a guess is used: flat faces up to 5 m above the ground, except vegetation (green in the photo) and water (dark in the glass map and bluish or greenish in the photo; pavement can also come out smooth, but grey) (the ground between buildings lights up, which looks close to a road network, but elevated roads stay dark). Points are placed at most one per cell in power-of-two cells about 2.5 pixels wide, on the 2D position along the axis the face points to most, blended smoothly with the next cell size. Each light gives a fixed amount of light, so a point's brightness is divided by the area of one pixel (capped at 2.5×) and the brightness per area does not depend on distance. Point size is set on screen, about one pixel (on distant oblique faces a pixel stretches along the view direction, so sizing in world units gave wide blobs). Brightness is spread as a few bright points and many dim ones, and 40 m blocks get more or fewer lights; windows also vary in the lit share per building and in brightness per run. Distant lights are dimmed to 80% from 1.5 to 12 km, on top of the haze. Window points start where one pixel spans 1.5–5 m, only on walls without windows in the glass map (none wherever there is any window, and window lights are 1.5× brighter to stand out; in the distance the window threshold is raised and window lights are dimmed only to 85%; on walls with windows, the farther away, the fewer windows are lit, down to about a third, at 2.5× the brightness, so lit windows show as points instead of being averaged to grey); street lights from 0.2–0.6 m. Unlit faces are darkened to 7% where a pixel spans 0.3–3 m. Earlier, white points were scattered everywhere, roofs included, and looked like noise (it was tried, but roads cannot be told apart from roofs, rivers and parks, so riverbanks and roofs turned orange). Motorways and trunk roads get car-light points (white headlights, red taillights), and the pavement glow is kept faint (from above, roads look like strings of lamp points rather than bands). Street points are occasionally neon blue or magenta. The haze is lit warm by the city (a light dome): the farther, the brighter, and the sky is brighter near the horizon. This follows a video of Tokyo at night seen from a plane. Tokyo Tower is floodlit orange from below (`LANDMARKS`: faces inside the tower's shape, from its position, height and base and top widths, light up; positions are Earth coordinates, 0.5 m steps in f32; the ground ellipsoid height is 56 m, measured by picking the mesh ground — it was 20 m, 35 m off, so the taper did not match and nothing above the observation deck lit up; above the main deck the Flyover mesh has almost none of the thin lattice, only fragments of the decks, so the tower shape is placed analytically and orange light is added where the view ray's closest approach to the tower axis falls within the tower width at that height and in front of the surface being drawn, with a 10 m beam and bracing pattern; in the sky it is added after the clouds; the upper lattice is mostly splats, so splats get the same floodlight above 130–150 m — below that the mesh lattice is lit and lighting the splats turned it into a flat orange sheet — modulated by the splat colour's brightness). All lights are 2× and unlit faces are darkened to 13%. Per-place brightness comes from NASA's Black Marble (2016, VIIRS; GIBS zoom-8 map tiles, about 500 m per pixel, `cache/blackmarble/`) and is stored in the road image's alpha (`cache/osm/night2/`; the viewer opens it without premultiplying). Where the city is dim (suburbs, valleys), street lights on small roads are nearly removed, main roads keep about half, and window and wall points are reduced (the idea of the flight-simulator add-on DarkStreets). Inside cities the satellite image is saturated white, so it makes no difference there. Nearby windows show rooms behind them (interior mapping, after Joost van Dongen, 2008): a box room 4.5 m wide, one floor high and 5 m deep sits behind each window, and the brightness depends on whether the view ray hits the ceiling, floor, side wall or back wall (bright ceiling, dark floor, darker with depth). OpenStreetMap also gives an image of water, commercial land, railways and stations, and stadiums (`/api/areas/z/x/y.png`, `areas` in `osm.py`, `cache/osm/areas2/`: red is water, green commercial land, blue railways (lines 90, yards 140, around stations 255), alpha 255 minus stadiums. Browsers drop the color of pixels whose alpha is 0 when decoding, so alpha is normally 255; the road image's alpha is at least 1). With it: (1) Light spill: the road, floodlight, commercial, station and stadium images blurred to 25–35 m (by choosing a mip level) serve as a light map, and the photo's color is taken as reflectance to light the ground and low walls (weaker with height, 1/e at 10 m; too strong and roads turn whitish). At night the glow starts at a brightness of 0.4 (with 0.2 the whole city blurred white), and star streaks come only from glow above 1. (2) Reflections on water: water (except bridges) is darkened and gets a reflection of the shore lights (roads and commercial land blurred to about 60 m) broken up by ripples: cells of 0.8 × 5 m, long toward the camera, take the fourth power of a random value (rarely bright), averaged in the distance (vertical screen streaks looked like rain). (3) Shopping streets: on commercial walls, ground-floor shop lights varying every 8 m in brightness and color (30% neon colors), and colored signs in 8% of 3 × 4 m cells on walls from 3 to 30 m; street lights are 1.8× there. (4) Stations and railways: sparse white lights along the tracks and bright white platforms (up to 18 m, for elevated lines). (5) Stadiums: 70% of stadiums and 35% of pitches (per 300 m cell) are lit by white floodlights that light the photo's color (green turf and so on); emitting light directly blew out to white. (6) On 40% of tall buildings (90 m or more), walls above 80 m are softly uplit in pale colors and the roof only faintly. (7) Car lights: white headlights and red taillights moving on motorways and trunk roads. The direction is perpendicular to the gradient of the blurred road image (which points to the road's center), so the two halves flow in opposite directions; cars moving away from the camera are red, approaching ones white. Time is `fr.ngrid.w` (wrapping every 10 minutes), and the view redraws every 0.1 s even when still (`?traffic=0` stops it). (8) Time of night (`?time=`, default 21): the amount of light from office windows, homes, shops, cars and stadiums follows hourly tables, interpolated linearly (late at night offices go dark, homes dim and stadiums turn off). (9) Distant ground without Flyover gets light points in proportion to the square of the night brightness (Black Marble; `/api/lights/z/x/y.png`, as is up to zoom 8 and cropped beyond, `cache/osm/lights/`), and their average glow where points are smaller than a pixel (only beyond 3–8 km from the camera). Following a photo of the night view from Abeno Harukas, the glow of the pavement itself is weak (roads read as strings of street and car lights), points and windows lean warm (warm white, amber, incandescent), and the sky is navy with a weaker brown haze at the horizon. Apartment corridors: on 35% of buildings in the city (30 m cells), the wall facing one chosen direction (north, south, east or west) gets a warm band of corridor lights on every floor (about a tenth of the floor height; fixtures every 3 m, uneven up close). Buildings lit by the city: unlit walls and roofs stay faintly visible, lit weakly in proportion to the photo's color. Car lights are denser, about one per 50 m². (10) Photographic finish (the final composite in `gpu-bloom.js`): star streaks from very bright spots horizontally, vertically and diagonally, a vignette darkening the corners by about 30%, and very faint grain.  At night the sky and haze brightness is scaled by 0.15 so the sky is almost black, and the night sky light is darker. `?windows=0.7` (default) sets the share of lit windows, `?windows=0` turns them off. At night a glow (bloom) is also added (`flyover/earth/gpu-bloom.js`): the scene is first drawn to a separate image, the part above a linear brightness of 0.2 is taken, blurred while halving it up to 6 times, added back up the levels and added to the scene. `?bloom=0` turns it off, `?bloom=1` uses it in daytime too, and `?bloom=0.5` and so on sets the strength (default 1). There are no signs, street lights or facade floodlights. The CesiumJS viewer has neither window lights nor glow
  - For lights with a sun (`morning`, `evening`, `?sun=`), the color and strength come from the atmosphere tables (`flyover/earth/sunlight.js`). The direct sunlight on the ground is the sunlight above the atmosphere × the transmittance from the ground to the top of the atmosphere (times the visible part of the sun when it touches the horizon), and the sky light comes from the table of sky light reaching the ground (both tables are made when the atmosphere is computed). At a sun height of 45° the result matches the photo (sunlit flat ground is 1, shadow is the ratio above), and the change from there follows the atmosphere. Like a camera's auto exposure, 70% of the change in brightness (green, averaged over flat ground and a wall facing the sun) is cancelled, up to 4×. For example, at a sun height of 9° the direct light is R 0.76, G 0.53, B 0.28 of that at 45°, so it is red, and its ratio to the sky light also follows the atmosphere. Until the tables are ready, and with `?atmo=0`, hand-picked values are used. `cloudy` and `night` have no sun and keep their hand-picked values
- **Regions registered by name**: Of the regions in the height-slab list, 53 (Paris, Seattle, Madrid, Milan and others) are named after places instead of `Reg_z9_X_Y`, and the viewer used to leave them out (it never requested their tiles). They are now assigned to the zoom 9 tiles their center and radius touch (225 tiles) and covered (`flyover/client.py`). Both the old and the new Flyover can be fetched there. Also, the `region` of the new Flyover (style 98) only has to be present; its value does not matter (0 returns the same tile)
- **JPEG textures**: In regions where the old Flyover shapes were repackaged (Paris, for example), the texture is a JPEG (512 px square) instead of HEIC. It starts with `FF D8 FF` right after the image item's header. The UV unit is the same as for HEIC (1 / (4 × image width or height)). All 217 height slabs at zooms 14–20 around the Eiffel Tower were read. These used to be rejected as "no texture" and filled in with C3M
- **Height map (style 99)**: The iOS 27 manifest also lists style 99, requested with zoom 14 tiles (`?style=99&v=<version>&x&y&z`; it responds only where the new Flyover exists and is empty elsewhere). It is a 512 px square 16-bit grey PNG holding the surface height of buildings and ground in 1 m steps (one pixel is about 4 m in Tokyo). The value is the height above the lowest point of that tile. Its difference from the mesh's ellipsoidal height is constant within a tile regardless of height (median 23.0 m in the Tokyo Station tile, median deviation 0.9 m) and differs per tile (Nagoya 32.7 m, New York −37.4 m, Denver 1,567 m). The base height is in 12 bytes appended after the end of the PNG (IEND): an f32 base height (ellipsoidal; Tokyo Station 22.06 m, Nagoya 31.73 m, New York −38.28 m, Denver 1,566.50 m), an f32 of 1.0 (height per unit value), `10 01` (16 bits, 1 channel) and a u16 of 12 (the length of this trailer). Height = base + value, which is 0.5–1 m below the mesh height (in all 6 tiles checked). What it is used for is unknown (the view does not use it)
- **Capture time (first item of part 2)**: The last 8 bytes of the 152-byte item are usually 0. In about a quarter of the tiles (here only zoom 20 tiles in Toyama, Takaoka, Kanazawa, Tokyo Station, Fukuoka, Sapporo, Cupertino and a few others) they hold a double Unix time (2025-01 to 2026-03), which appears to be when the aerial photos were taken (98% of zoom 20 tiles have it, zoom 13–19 tiles never do). Like Google Earth's imagery date, the viewer shows the capture date of the zoom 20 tile at the screen centre in the bottom bar (if that tile is not loaded it asks the server via `/api/captured/20/x/y`, which fetches just one height slab of it). All of them fall between 8.9 and 14.7 h local solar time, and neighbouring tiles differ by seconds to minutes (the flight order). Casting shadows with the sun direction computed from that time and place matches item 6 (the sunlit map) with a median correlation of 0.55, almost the same as the best direction found by searching (0.56; 38 tiles in 8 regions, median angle between the two 7°). Shifting the time by 3 hours drops it to 0.34, and the true time is better in 35 to 37 of 37 tiles. The 3 f32 before the time are usually 0.5 each; in tiles with a time they are bluish per-tile values (e.g. 0.013, 0.018, 0.029; blue about 1.4 × red). They follow the sun height somewhat (correlation 0.55) but the photo's shadow-to-sunlit ratio only weakly (0.33), so their meaning is unknown
- **What is unknown**: The true meaning of splat value 1 (item 8 seems to be a glass map, but how Apple uses it is unknown), and how Apple uses value 4 (the sun value) when drawing (with the 3 Apple screenshots at hand, not using it matches best; the view uses none of the 4 values now; checking further needs screenshots at different times of day). ## Export options

```bash
python scripts/export.py 36.5722 136.6680 --out out/higashi-chaya   # Higashi Chaya District, Kanazawa
python scripts/export.py --bbox 34.6418 135.3729 34.6601 135.4045 --r3d --quality 100 --block 15 --out out/yumeshima   # all of Yumeshima, in blocks
python scripts/serve.py out                                          # http://localhost:8000/higashi-chaya/
```

For the 9×9 tiles around Higashi Chaya (about 280 m square, 88 tiles, 150,000 triangles), fetching and exporting takes about 10 seconds.

| Option | Default | Meaning |
|---|---|---|
| `--out` | (required) | Output folder |
| `--zoom` | 20 | Tile detail (at 20, one tile is about 30 m square) |
| `--radius` | 4 | How many tiles to fetch in each direction from the center tile (4 gives 9×9 tiles) |
| `--bbox` | none | Give the area as south, west, north, east latitude/longitude instead of a center and `--radius` |
| `--r3d` | off | Use the new Flyover (iOS 27); only tiles without it, or that fail to parse, use the old Flyover |
| `--block` | none | Write N×N tiles per folder, plus an index page (a large area on one page does not fit in GPU memory) |
| `--jobs` | 8 | Number of tiles fetched at once |
| `--obj` | none | Also export OBJ (give a file name, e.g. `--obj out/kanazawa.obj`). With `--r3d`, splats such as trees become triangles with vertex colors (`splats`). OBJ has no transparency, so their soft edges are lost |
| `--glb` | none | Also export glb (glTF) (give a file name, e.g. `--glb out/yumeshima.glb`). With `--r3d`, splats are included as semi-transparent triangles with vertex colors and soft edges, as in the viewer. Opens in Blender, three.js, Windows 3D Viewer, and others |
| `--quality` | 90 | JPEG quality of the images (95 or more keeps full color resolution) |
| `--hevc` | none | Write new-Flyover images as HEVC instead of JPEG (the browser decodes them on the GPU; image files are about 1/5 the size, and photos are not recompressed, so no quality loss; only viewable in browsers that can decode HEVC on the GPU) |
| `--cache` | `cache` | Where fetched data is saved |

## Comparison with the Go version

The Python reader has been checked to **match the Go version bit for bit** on real tiles (88 tiles in Kanazawa and 121 in Shibuya, 209 in total). To check again:

```bash
git clone https://github.com/retroplasma/flyover-reverse-engineering
cd flyover-reverse-engineering
git apply ../flyover-web/tools/retroplasma-2026.patch && rm -rf vendor
go build -o dump-json.exe ./cmd/dump-json
cd ../flyover-web
python scripts/compare_go.py ../flyover-reverse-engineering/dump-json.exe cache/c3m/*
```

The patch also makes the Go version itself work against today's servers (`go run ./cmd/export-obj 36.5722 136.6680 20 4 4`).

The browser readers (`flyover/earth/c3m.js`, `r3d.js`) have also been checked to match the Python versions bit for bit (3,909 tiles from `cache/c3m/` and 1,416 from `cache/r3d/`; for R3D also splats, images and capture time). They run under Node.js for the comparison:

```bash
python scripts/check_c3m_js.py            # every 40th file in cache/c3m/ (change with --every)
python scripts/check_c3m_js.py --r3d      # cache/r3d/
```
